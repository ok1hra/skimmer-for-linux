A fix release for CW v4: it no longer runs out of memory, and a skimmer that loses its own stream picks it up again by itself.

The decoders' output and the feed are as in v0.8.13, byte for byte.

## CW v4 ran out of memory

- **What happened:** with CW v4 on, the skimmer's memory grew by about 10 GB an hour on a 6-band skimmer, until the system killed it (every 2–2.5 h on a 32 GB machine).
- **Why:** each of v4's channels kept a row of numbers for every moment since the station on it last keyed, even while the channel was quiet. A channel that stayed quiet for hours took that much memory at its next over and kept it.
- **Now:** a quiet stretch takes no memory. The decoded text is exactly what it was before; only the storage changed. A 10-minute recording replayed through v4 now stays at 128 MB. Before, it grew from 130 to 464 MB.

If you switched back to CW v3.1 because of this, you can switch to v4 again: Settings → Decoding → CW engine, or `[decode] engine=v4`.

## A lost stream that was still ours

- **What happened:** when the skimmer stalled (here, short of memory), it stopped reading its Red Pitaya for a few seconds and took that as "another client took the radio". The radio kept streaming to the skimmer's closed port, so it answered *busy*, and every restart gave up with "no free radio" until someone sent the radio a stop by hand.
- **Now:** the skimmer remembers the stream it lost. When it next finds the radio busy, it listens on its old port. If the radio's stream still arrives there, it is its own, so the skimmer stops it and starts the radio again, with no restart. A stream of another client goes to that client's address, so it is never stopped.

## Install

A skimmer on v0.8.8 or later with `[update] mode=auto` (the default) installs this release by itself at its update hour. Settings → Updates → *Install now* does it at once. By hand:

```sh
mv skimmer-headless-0.8.14-x86_64.AppImage skimmer-headless-x86_64.AppImage
chmod +x skimmer-headless-x86_64.AppImage
./skimmer-headless-x86_64.AppImage
```
